M0.1

Git and the GitHub workflow

5 concepts
look up: git, commit, repository

Git: commits and history

Git records a project as a chain of commits. Each commit is a snapshot of every file, with a message saying what changed and why. The chain is the history, and you can return to any point in it.

In Neext: git log --oneline shows our history. Each line on main is one finished milestone.

Check yourself: what's in a commit?

A snapshot of the files, plus a message, an author and a link to the commit before it. That link is what makes history a chain.

Used in every layer
look up: git branch, remote, push, pull

Branches and GitHub

A branch is a separate line of commits where you can work without touching main. GitHub holds the shared copy of the repo, called a remote. You push your commits up to it and pull other people's down.

In Neext: every milestone gets a branch like docs/m0.6-field-guide. After a merge, git switch main && git pull brings your copy up to date.

Check yourself: why not just work on main?

Unfinished work would sit in the official copy. A branch keeps half-done work separate until it's been checked and signed off.

Used in every layer
look up: pull request, issues, closing keywords

Issues, pull requests and the board

An Issue describes a piece of work. A pull request (PR) proposes merging a branch into main, with the changes shown for review. Writing Closes #10 in a PR closes Issue #10 automatically when the PR merges. The project board shows each Issue's status, and Milestones group Issues by layer.

In Neext: Issues #1–#4, #9 and #10 sit under "Layer 0 · Foundations". Each PR description doubles as a learning write-up.

Check yourself: what moves a card to "Done" on the board?

Merging a PR that says Closes #N. GitHub closes the Issue, and the board's built-in automation moves its card to Done.

Used in every layer
look up: GitHub rulesets, branch protection

A protected main

A ruleset is a set of rules GitHub enforces on a branch. Ours says changes to main must come through a PR, and nobody can force-push, delete it or bypass the rules, the repo owner included. It also requires the lint check to pass.

In Neext: pushing an unapproved commit straight to main was rejected. One twist: pushing a commit that an open, mergeable PR already contains counts as merging that PR. That's how PR #5 got merged by the demo push.

Check yourself: why are 0 approvals required, if the point is review?

GitHub won't let you approve your own PR, so on a solo repo, requiring an approval would lock everyone out. The protection comes from forcing every change through a PR and the CI check, with you choosing to merge.

Again in L2: prod changes only via PR
look up: squash merge, Conventional Commits

Squash merging and commit titles

A squash merge combines all of a PR's commits into one new commit on main, titled with the PR's title. Conventional Commits is a title format (feat:, fix:, docs:, ci:, chore:) that makes history readable, and lets tools generate changelogs from it.

In Neext: main has one line per milestone. Afterwards git says your old branch is "not fully merged", because the squash created a brand-new commit. Check with git diff, then delete the branch with -D.

Check yourself: why does git think a squash-merged branch isn't merged?

The branch's own commits never reached main. A new, combined commit did. The content is the same, but the commits are different, and git compares commits.

Used in every layer
M0.2

Toolchain and containers

5 concepts
look up: Homebrew, formula vs cask, Brewfile

Toolchain as code

Homebrew installs software on a Mac. A formula is a command-line tool and a cask is a desktop app. The Brewfile lists every tool the project needs, and brew bundle installs the lot. The setup becomes a file you can check, share and repeat, rather than steps you have to remember.

In Neext: Brewfile has 10 tools. brew bundle check says whether anything's missing.

Check yourself: what's the advantage over a list of install commands in the README?

The Brewfile can be run and checked automatically, and it can't drift from what's actually installed without brew bundle check noticing.

Grows each layer
look up: container image, container, Docker

Images and containers

An image is a sealed, read-only package: a program plus everything it needs to run. A container is an image that's running, isolated from everything else on the machine. Many containers can start from one image.

In Neext: docker images lists the kits and docker ps lists what's running. Even the cluster's nodes are containers.

Check yourself: you delete a container. Is the image gone?

No. The image is the kit, and stays until you remove it with docker rmi. You can start a fresh container from it at any time.

Again in L1: we build our own images
look up: Linux kernel, Docker Desktop VM

Why Docker Desktop is a virtual machine

Containers share the Linux kernel of the machine they run on. macOS isn't Linux, so Docker Desktop runs a small Linux virtual machine and every container lives inside it. That VM gets a fixed share of your Mac's memory.

In Neext: capped at 14 GB. It reports 13.6 GiB, because the VM's own kernel keeps a slice for itself.

Check yourself: why can't macOS run Linux containers directly?

A container is just an isolated process, and it uses the host's kernel. Linux containers need a Linux kernel, so on a Mac one has to be provided by a VM.

Again in L5: memory stress drills
look up: CPU architecture, arm64, multi-arch images

arm64 and multi-arch images

Programs are built for a CPU architecture. Your Mac and our Oracle prod server are both arm64, while most cloud servers are x86 (amd64). Popular images are multi-arch: one name points to a list of builds, and Docker pulls the one that matches your machine.

In Neext: docker run --rm alpine uname -m printed aarch64, the Linux name for arm64. CI also runs on arm64.

Check yourself: why does it matter that dev and prod are both arm64?

We build one image and run it in both places. Mismatched architectures would need two builds, or slow emulation.

Again in L1 and L2
look up: JDK, LTS, JAVA_HOME, transitive dependency

Java versions and JAVA_HOME

The JDK is the kit for building and running Java. LTS (long-term support) releases like 25 get years of fixes, while the releases in between, like 27, are short-lived. JAVA_HOME tells Java tools which JDK to use.

In Neext: Homebrew's Maven brought Java 27 in as a transitive dependency: you didn't ask for it, but something you asked for did. Setting JAVA_HOME pins Java 25.

Check yourself: mvn -v says Java 27. What do you check?

Whether JAVA_HOME is set in that terminal. Open a new one, or run source ~/.zshrc.

Again in L1: the catalog service
M0.3

Kubernetes

8 concepts
look up: Kubernetes, desired state, reconciliation loop

What Kubernetes is for

Kubernetes runs containers across many machines. You declare the desired state ("one copy of this, reachable on that path"), and Kubernetes keeps making reality match it. This is the reconciliation loop: if a container dies, Kubernetes notices the gap and starts another.

In Neext: every .yaml in platform/ is a desired-state declaration, and kubectl apply hands it over.

Check yourself: you delete a Pod managed by a Deployment. What happens?

A new one appears within seconds. The desired state still says "1 copy", so the reconciliation loop replaces it.

The basis of every later layer
look up: control plane, worker node, k3s, k3d

Clusters and nodes

A cluster is a group of machines called nodes. The control plane is the brain: it runs the API that takes orders and decides where things run. Workers run the actual containers. k3s is a lightweight Kubernetes, and k3d runs k3s with each node as a Docker container.

In Neext: 1 control plane and 2 workers, on k3s v1.35.9, the same version prod will run. kubectl get nodes lists them.

Check yourself: why two workers rather than one?

So we can practise what multi-node clusters do: spread work out, drain a node, and survive losing one. Layers 6 and 8 rely on this.

Again in L2: prod k3s
look up: Pod, Deployment, ReplicaSet

Pods and Deployments

A Pod is the smallest thing Kubernetes runs: one container, sometimes a few working together. You rarely create Pods directly. A Deployment says "keep N copies of this Pod running", and manages a ReplicaSet that does the counting. Changing a Deployment rolls out new Pods gradually.

In Neext: platform/smoke-test.yaml declares a Deployment with replicas: 1. The Pod's name, smoke-77f9d8f4cd-…, includes the ReplicaSet's ID.

Check yourself: Pod or Deployment, which would you scale to handle more traffic?

The Deployment, by raising replicas. Pods are disposable. In Layer 6, the autoscaler changes this number for you.

Again in L1 and L6
look up: Service, Ingress, ingress controller, Traefik

Services, Ingress and Traefik

Pods come and go, and their addresses change. A Service is a stable name that always forwards to whichever matching Pods exist right now. An Ingress is a rule for outside traffic, such as "requests to / go to Service smoke". An ingress controller enforces those rules; k3s ships with Traefik.

In Neext: follow the animated line in diagram A: localhost:8080 → Traefik → Service → Pod.

Check yourself: why not send traffic straight to a Pod's address?

That address dies with the Pod. The Service's name stays the same, and it spreads traffic across all the healthy copies.

Again in L1; replaced by a gateway in L3
look up: namespace

Namespaces

A namespace divides one cluster into separate areas. Names only have to be unique within a namespace, and rules and quotas can be applied per namespace.

In Neext: neext-local belongs to Tilt (your uncommitted code) and neext-dev to Argo CD (a mirror of main). They're kept apart, because Argo CD undoes anything that isn't in git.

Check yourself: why must Tilt and Argo CD never share a namespace?

Argo CD would treat every Tilt deploy as drift and revert it within minutes. The two would fight forever.

Again in L1 and L2
look up: readiness probe, resource requests and limits

Health checks and resource limits

A readiness probe is a check Kubernetes runs before sending a Pod traffic, such as "does /health answer?". Requests reserve CPU and memory for a container, and limits cap them. Without limits, one greedy container can starve the rest.

In Neext: even the tiny smoke Pod declares 16Mi requested and 32Mi at most. It's a house rule for every workload.

Check yourself: a container exceeds its memory limit. What happens?

Kubernetes kills it, called being "OOMKilled" (out of memory), and starts it again. You'll see this in Layer 1 if Java isn't tuned to its limit.

Again in L1 (JVM tuning) and L6
look up: kubeconfig, kubectl context

kubeconfig and contexts

kubectl reads a file called kubeconfig listing the clusters it knows about. Each entry is a context, and one of them is "current". Run a command without naming a context and it goes to whichever is current, which may not be the one you think.

In Neext: the Makefile always passes --context k3d-neext. Once prod exists, a wrong current context could change prod by accident.

Check yourself: why name the context even when there's only one cluster?

The habit has to be in place before the second cluster (prod) arrives in Layer 2. Accidents happen the first time you forget.

Critical from L2
look up: Makefile, idempotency, smoke test

Makefile, idempotency and smoke tests

The Makefile is the repo's list of shortcuts: make shows them all. A command is idempotent if running it twice is as safe as running it once. A smoke test is a quick end-to-end check that the basics work, named after powering on new hardware and checking nothing starts smoking.

In Neext: make cluster-up is idempotent. make smoke deploys a test page, checks it answers, then removes it.

Check yourself: why does idempotency matter for automation?

Scripts get re-run after failures and retries. If running something twice could break it, every retry becomes a risk.

M0.4

Continuous integration

4 concepts
look up: continuous integration, GitHub Actions, required status checks

CI and GitHub Actions

Continuous integration means every change is checked automatically before it lands. GitHub Actions runs workflows. A workflow has jobs, a job has steps, and each job runs on a fresh machine called a runner. A required check must pass before GitHub allows the merge.

In Neext: .github/workflows/ci.yml has one job, lint, on a free arm64 runner, taking about 8 seconds. It runs make lint, the same command you run locally.

Check yourself: why does CI run make lint rather than its own commands?

So a green result on your Mac means a green result in CI. One definition of "passing", and no drift between the two.

Grows in L1: tests and image builds
look up: YAML, linter, JSON Schema, kubeconform

YAML: format vs meaning

YAML is the text format for almost all our config: key: value pairs, indentation for nesting, and - for list items. A linter (yamllint) checks the format. A schema check (kubeconform) checks the meaning: is this a real Kubernetes object, with real field names?

In Neext: replica: 1 is perfectly good YAML, but kubeconform rejected it, because the field is replicas. That was the M0.4 demo.

Check yourself: what's the "Norway problem"?

Some YAML readers treat a bare no as false. A list of country codes containing NO then silently turns Norway into "false". Our lint rules only allow true and false as booleans.

Every layer: Helm, Argo CD and more
look up: software supply chain, SHA pinning, least privilege

Supply-chain hygiene

Your build trusts code written by other people. Pinning by SHA fixes each GitHub Action to an exact commit, which can't be swapped, rather than a tag like v7, which can be moved. Checksums prove a download wasn't tampered with. Least privilege means giving the workflow only the permissions it needs.

In Neext: actions/checkout@3d3c42e…, a sha256sum --check on the kubeconform download, and permissions: contents: read.

Check yourself: why is a tag riskier than a SHA?

Whoever controls the action can point the tag at different code later, as happened in the 2025 tj-actions compromise. A SHA always means exactly the same code.

Again in L1: our own images
look up: git revert vs git reset, Dependabot

Undoing safely, and Dependabot

git revert undoes a commit by adding a new commit that reverses it, so history stays intact. git reset rewrites history, and on a branch others have already seen, that needs a force-push. Dependabot opens PRs when the things we depend on release updates.

In Neext: the broken replica commit was reverted, not erased. Dependabot will open a weekly ci: PR for Actions updates.

Check yourself: when is reset fine?

On commits nobody else has seen yet, like the stray empty test commit on your local main, which we removed with git reset --keep.

Used whenever we undo
M0.5

Vulnerability management

4 concepts
look up: CVE, CVSS, software composition analysis

CVEs and what the counts mean

A CVE is a publicly catalogued security flaw, scored for severity (CVSS: low to critical). Scanners list the libraries inside an image, a technique called software composition analysis, and match their versions against known CVEs. They see which version is present, not whether the program ever uses the faulty part.

In Neext: Docker Scout showed 66 criticals. Nearly all traced to four Go libraries compiled into tools other people build.

Check yourself: is an image with 34 criticals four times as risky as one with 8?

Not necessarily. It depends on whether the flawed code can be reached, and by whom. A count tells you where to look, not how much danger you're in.

Every layer kickoff: make scan
look up: attack surface, 127.0.0.1 vs 0.0.0.0

Exposure: who can reach it?

A program listening on 127.0.0.1 (localhost) only accepts connections from the same machine. On 0.0.0.0 it accepts them from every network your machine is on. Shrinking what outsiders can reach is attack surface reduction.

In Neext: port 8080 was open to the whole Wi-Fi, in front of the most vulnerable image. A one-word fix took it off the network. Now every port binds to 127.0.0.1.

Check yourself: why did that fix matter more than the upgrades?

A flaw nobody can reach can't be exploited. Cutting off access protected against all of k3d-proxy's CVEs at once, including ones that don't have a fix yet.

Again in L2 (Tailscale) and L3 (going public)
look up: semantic versioning

Patch, minor, major

Semantic versioning reads MAJOR.MINOR.PATCH. A patch bump (1.35.5 → 1.35.9) is fixes only. A minor bump (1.35 → 1.37) adds features. A major bump (registry 2 → 3) may break things. Patches are safe to take promptly; minors and majors need care.

In Neext: we took the k3s patch release straight away, and tested the registry's major upgrade with a real image push before trusting it.

Check yourself: why not jump k3s straight to 1.37?

A minor jump changes features and APIs, and prod has to match dev. That's a deliberate decision for both environments, not a quick security fix.

Every upgrade
look up: risk acceptance, vulnerability register

Accepting risk, on the record

Some flaws can't be fixed yet, because the fix has to come from the people who build the software. Risk acceptance means deciding to live with one for now, writing down why, and saying when you'll look again. Ours also had a blind spot: images running inside k3s never appear in Docker Desktop.

In Neext: docs/vulnerabilities.md lists each accepted CVE and its "re-check when" trigger. make scan covers both image stores. Decision 019 sets the policy.

Check yourself: why didn't Traefik's CVEs show in Docker Desktop?

Traefik's image lives in k3s's own image store, inside the node containers, not in Docker's. Docker Desktop only lists Docker's store.

Operations

Running it day to day

Start and stop

  1. Open Docker Desktop and wait until it's running.
  2. make cluster-up confirms or creates the cluster.
  3. make smoke checks the whole path.

When you.re done, you can leave it running (about 1.1 GB), quit Docker Desktop (the cluster pauses and comes back next time), or run make cluster-down (deletes it; rebuilt in under a minute).
